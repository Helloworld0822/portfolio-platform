01 / BACKGROUND & BOTTLENECK

1. 왜 기존 배치 기반 스케줄러로는 한계가 있었는가?

기존의 waynudge 서비스 초기 버전은 Node.js 기반의 cron 워커가 2분 간격으로 데이터베이스에서 활성 사용자들의 출퇴근 동선을 일괄 조회하고, 공공데이터 포털 및 수도권 대중교통 실시간 API로 HTTP 폴링을 수행하는 구조였습니다.

그러나 사용자가 1,000명을 넘어가던 시점부터 수도권 광역버스 도착정보 시스템(TOPIS) 및 서울열린데이터광장의 RPS(Requests Per Second) 제한에 번번이 걸리기 시작했습니다. 특히 08:10 ~ 08:35 사이의 출근 집중 시간대에는 단 3초만 지각해도 알림 품질이 붕괴되는 특성이 있었고, 다음과 같은 3가지 치명적 병목이 발생했습니다:

  • 1. Burst Traffic 누적: cron 배치가 도는 순간 서드파티 API로 400여 건의 동시 쿼리가 쏟아져 HTTP 429 Too Many Requests 반환율이 34%까지 급증.
  • 2. 스케줄러 오버헤드: Node.js 이벤트 루프에서 수천 건의 지오메트리 계산(Haversine 거리 및 도보 도착 추정)을 단일 스레드로 연산하며 p99 지연이 1.8초를 돌파.
  • 3. 불필요한 중복 쿼리: 동일한 강남역 방향 9401번 버스를 대기 중인 사용자가 28명일 때, 28번의 독립적 API 호출이 중복 발생.
info
핵심 전환점: Pulling에서 Reactive Event Pipeline으로

"사용자가 원할 때 긁어오는" 기존 구조를 폐기하고, 버스와 지하철 노선의 실시간 상태 이벤트를 백그라운드에서 싱글톤 스트림으로 통합 소비(Consuming)한 뒤, 인메모리 공간 색인(Spatial Index)에 샤딩 저장하여 구독자에게 즉각 매칭하는 Rust 엔진으로의 전면 재작성을 결심했습니다.

02 / PIPELINE ARCHITECTURE

2. Tokio 비동기 채널(mpsc) 기반 스트리밍 파이프라인 설계

Tokio 런타임의 tokio::sync::mpsc 채널과 멀티 스레드 스케줄러(Work-stealing runtime)를 채택하여, 네트워크 I/O 작업(Ingestion)과 CPU 집약적인 경로 매칭(Routing Solver) 작업을 엄격히 물리 스레드 풀 단위로 분리했습니다.

src/engine/dispatcher.rs
Rust (Tokio 1.36) 
1// Ingestion Event와 Worker Pipeline 분리2pub struct CommuteDispatcher {3    tx_transit: mpsc::Sender<TransitEvent>,4    subscribers: Arc<DashMap<RouteId, SmallVec<[UserSubscription; 8]>>>,5}67impl CommuteDispatcher {8    pub fn spawn_worker(mut rx: mpsc::Receiver<TransitEvent>, store: Arc<RouteShardedState>) {9        tokio::spawn(async move {10            while let Some(event) = rx.recv().await {11                // Non-blocking lock-free shard access12                if let Some(users) = store.get_active_commuters(&event.route_id) {13                    for user in users.iter() {14                        let eta_diff = event.predict_arrival_delta(&user.departure_node);15                        if eta_diff.abs() >= Duration::from_secs(60) {16                            // FCM 알림 큐로 비동기 디스패치 (Zero Allocation)17                            store.push_nudge_event(user.id, eta_diff).await;18                        }19                    }20                }21            }22        });23    }24}

2.1 Backpressure 제어와 버퍼 용량 사이징

초기에는 버퍼 무제한 채널(unbounded_channel)을 사용했으나, TOPIS 서버가 간헐적으로 지연 응답을 쏟아낼 때 Rust 프로세스 힙 메모리가 순간적으로 380MB까지 치솟는 현상을 겪었습니다.

이에 버퍼 크기를 channel(10,000)으로 명시적 바운딩하고, 채널이 80% 이상 찼을 경우 즉시 서드파티 요청 주기를 능동적으로 늦추는 적응형 레이트 리미터(Adaptive Rate Limiter)를 결합했습니다.

03 / MEMORY CONCURRENCY

3. DashMap & Lock-free 인메모리 샤딩 구조

수많은 비동기 태스크가 동시에 사용자의 위치 및 구독 노선 목록을 읽고 갱신해야 합니다. 표준 라이브러리의 Arc<RwLock<HashMap<...>>>를 사용할 경우, 쓰기 작업(새 유저 구독 등록)이 발생하는 순간 모든 읽기 작업 스레드가 블로킹되는 RwLock 경합(Lock Contention)이 극심해집니다.

3.1 RwLock 경합(Contention) 프로파일링

perf와 flamegraph로 프로파일링한 결과, 전체 CPU 시간의 무려 27.8%가 sys_futex 대기 상태에 묶여 있었습니다. 이를 해결하기 위해 메모리를 64개의 독립 버킷으로 쪼개어 제어하는 DashMap을 도입했습니다:

Concurrency Lock Latency Under 20,000 RPS (Lower is Better) Unit: Microseconds (μs)
Standard `Arc<RwLock<HashMap>>` 4,820 μs (극심한 락 병목)
Tokio Async `Arc<RwLock<HashMap>>` 1,450 μs (스케줄러 오버헤드 잔존)
64-Shard Lock-free `DashMap` (최종 도입) 82 μs (58배 개선)
04 / PERFORMANCE & BENCHMARK

4. 실제 부하 벤치마크 및 Tail Latency (p99 14ms) 달성

동시 가상 출퇴근 사용자 50,000명이 등록되어 있고, 분당 12,000건의 교통 상태 변경 이벤트가 스트리밍되는 스트레스 환경에서 k6와 wrk를 사용해 종합 벤치마크를 수행했습니다.

Median Latency (p50) 240 ms 28 ms 2.1 ms

메모리 점유 (Resident RSS) 410 MB 115 MB 28.4 MB

Go 언어로 작성한 프로토타입 역시 우수한 성능을 보여주었으나, 5만 개 커넥션 유지 중 일어나는 주기적인 가비지 컬렉터(STW GC pause) 순간에 최대 80ms 이상의 튐 현상이 관찰되었습니다. 반면 Rust는 컴파일 타임의 RAII와 제로 코스트 추상화 덕분에 99.9%의 요청이 균일하게 14ms 이하로 완주했습니다.

05 / RETROSPECTIVE & NEXT

5. 프로덕션 회고와 다음 개선 과제

이번 엔진 개편을 통해 배포 환경 비용을 AWS c5.large 4대에서 단일 t4g.small 인스턴스 1대로 감축할 수 있었으며, 월 서버 인프라 유지 비용이 $210에서 $14 수준으로 93% 이상 절감되었습니다.

현재 직면한 다음 기술적 도전 과제는 다음과 같습니다:

  1. 분산 노드 오케스트레이션: 향후 전국 단위 대중교통 노선 확장을 대비해 Raft 합의 알고리즘 기반 샤드 클러스터 구축 (시리즈 4편 예정)
  2. SIMD 가속 거리 계산: packed_simd를 이용한 대규모 좌표 일괄 투영 최적화
  3. eBPF 기반 네트워크 모니터링: 패킷 수신부터 Tokio 채널 진입까지의 커널 지연 추적
