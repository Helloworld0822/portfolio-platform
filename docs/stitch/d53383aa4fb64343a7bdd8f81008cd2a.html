Rust와 Tokio 비동기 런타임으로 구축한 실시간 커뮤트 엔진: p99 지연 시간 91% 단축기

수도권 8개 대중교통 공공 API의 간헐적 지연과 출퇴근 시간대 초당 수만 건의 매칭 스레드가 유발하던 V8 GC 스파이크를 분해하고, Lock-free Ringbuffer 기반 Tokio Actor 아키텍처로 전환한 엔지니어링 기록입니다.

전재민 @helloworld0822
2024.12.18 · schedule 8 min read · Verified Benchmarks
𝕏
#Rust #Tokio #Performance #LockFree #ZeroCopy #WayNudge
insights Executive Summary

기존 Node.js 기반 실시간 대중교통 배차 매칭 서비스인 WayNudge v1은 아침 8시 러시 아워 동안 초당 42,000건의 위치 핑을 처리할 때 Node.js V8 힙 가비지 컬렉션(GC Pause)으로 인해 p99 응답 시간이 최대 1,480ms까지 치솟았습니다. 본 글에서는 이 문제를 진단하고, Rust와 Tokio Multi-threaded Runtime, Crossbeam 기반 Lock-free Ringbuffer를 도입해 p99 지연 시간을 128ms로 91.3% 단축한 설계와 구현 내역을 상세히 공유합니다.

01

대중교통 공공 데이터의 태생적 한계와 병목 정의

수도권 버스 및 지하철 실시간 도착 정보를 제공하는 지자체 공공 API는 매우 강력하지만, 네트워크 계층에서 두 가지 치명적인 결함이 존재합니다. 첫째, 응답 지연 시간의 불규칙성(Jitter)입니다. 동일한 정류장 조회 엔드포인트도 25ms에서 4,500ms까지 들쑥날쑥하며 일시적인 타임아웃이 잦습니다. 둘째, 데이터 포맷이 정형화되지 않은 대형 XML/JSON 페이로드로 매번 200KB 이상을 반환한다는 점입니다.

사용자 수만 명이 실시간 길안내와 도착 알림을 요청할 때, 중앙 서버는 매 초 수천 개의 업스트림 공공 HTTP 세션을 유지하며 페이로드를 파싱해야 합니다.

02

v1(Node.js)의 병목: V8 Event Loop GC Stall

WayNudge v1은 Node.js 클러스터 모드로 구동되었습니다. Fastify와 Redis Pub/Sub을 엮어 초당 15,000건까지는 쾌적했으나, 특정 역(예: 강남역, 사당역 환승구역)의 실시간 집중 모니터링 이벤트가 폭증하면서 프로세스 힙 크기가 1.4GB를 넘나들기 시작했습니다.

결과적으로 V8의 Scavenge와 Mark-Sweep-Compact 가비지 컬렉터가 주기적으로 싱글 스레드를 멈춰 세웠습니다(Stop-the-world). 이때 인바운드 웹소켓 하트비트가 끊기며 클라이언트는 대량 재접속 폭풍(Thundering Herd)을 일으켰고, p99 지연 시간은 기하급수적으로 폭증했습니다.

warning
메모리 할당 단편화와 복사 오버헤드

JSON 문자열 파싱 과정에서 생성되는 수백만 개의 임시 JavaScript 객체들이 Young Generation 힙을 순식간에 채웠고, C++ 버퍼와의 메모리 복사(Memory Copy)로 인해 CPU 코어가 100%에 고정되는 병목이 확인되었습니다.

03

Zero-Copy와 Lock-Free Ringbuffer 설계

Rust 전환의 핵심 목표는 "런타임 힙 할당(Heap Allocation)을 핫 패스(Hot Path)에서 완전히 제거하는 것"이었습니다. 이를 위해 고정 크기의 원형 버퍼(Ringbuffer)를 메모리에 사전 할당하고, 네트워크 소켓에서 읽어온 원시 바이트 슬라이스를 별도 복사 없이 제로카피로 인메모리 파싱했습니다.

engine/src/ringbuffer.rs 
use crossbeam_queue::ArrayQueue;
use std::sync::Arc;
use bytes::Bytes;

/// 고정 용량 65,536 슬롯의 Lock-free 수신 링버퍼 구조체
pub struct CommuteEventDispatcher {
    queue: Arc<ArrayQueue<TransitPacket>>,
}

impl CommuteEventDispatcher {
    pub fn new(capacity: usize) -> Self {
        Self {
            queue: Arc::new(ArrayQueue::new(capacity)),
        }
    }

    #[inline(always)]
    pub fn push_packet(&self, payload: Bytes) -> Result<(), DispatchError> {
        let packet = TransitPacket::zero_copy_parse(&payload)?;
        self.queue
            .push(packet)
            .map_err(|_| DispatchError::QueueFull)
    }
}

Listing 3.1: ArrayQueue를 통한 락 경합(Mutex Lock Contention) 없는 패킷 분배 로직.

04

Tokio Multi-threaded Runtime & MPSC Actor

수만 개의 SSE(Server-Sent Events) 스트림 클라이언트와의 영속 연결은 Tokio의 경량 그린 스레드(Task)가 전담하도록 설계했습니다. 운영체제 네이티브 스레드 1개가 수천 개의 비동기 태스크를 협동 스케줄링(Cooperative Scheduling)하므로 컨텍스트 스위칭 오버헤드가 극단적으로 낮습니다.

engine/src/actor.rs Tokio Worker Core 
#[tokio::main(flavor = "multi_thread", worker_threads = 8)]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let (tx, mut rx) = tokio::sync::mpsc::channel::<RouteUpdate>(100_000);

    // 백그라운드 실시간 공공 스트림 수신 워커
    tokio::spawn(async move {
        let mut stream = TransitClient::connect_stream().await;
        while let Some(update) = stream.next().await {
            let _ = tx.send(update).await;
        }
    });

    // 라우팅 연산 전용 스케줄러
    while let Some(event) = rx.recv().await {
        tokio::spawn(process_commute_route(event));
    }
    Ok(())
}

06

엔지니어링 교훈과 결론

언어 전환은 결코 가벼운 결정이 아니었습니다. Rust의 엄격한 라이프타임 검사와 소유권 모델은 초기 작성 속도를 떨어뜨렸지만, 배포 후 프로덕션 환경에서 발생하던 원인 불명의 동시성 레이스 컨디션과 메모리 누수를 단 한 건도 남김없이 컴파일 단계에서 차단했습니다.

특히 외부 API의 통제 불가능한 지연을 대면할 때는 동기 블로킹 호출을 결코 메인 파이프라인에 섞지 않고, 무제한 큐 대신 역압(Backpressure)이 보장되는 링버퍼로 제어하는 것이 p99 지연 시간 안정성의 핵심임을 체득했습니다.
