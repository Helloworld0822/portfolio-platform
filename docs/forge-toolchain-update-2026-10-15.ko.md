# Portfolio의 Forge 도구체인 업데이트

Forge 서버와 브라우저 프런트엔드에 compiler `a750b60`, runtime `dcbb192`,
stdlib `6aa2866`을 적용하고 호환성을 검증했다. 기존 수동 복사 방식은
커밋 고정·내용 해시·의존 버전 검사·실패 시 기존 번들 보존을 지원하는
업데이트 명령으로 바꿨다.

```sh
python3 scripts/update-forge-toolchain.py --revision main
python3 scripts/update-forge-toolchain.py --check
```

`main`은 실행 시점의 특정 커밋으로 고정된다. compiler의 선언에서 맞는
runtime·stdlib을 함께 선택하고 원본 CMake·라이선스·테스트를 보관한다.
빌드는 네트워크로 언어 버전을 자동 변경하지 않는다. 로컬 저장소의 커밋만
내보내는 `--source-root`도 지원한다. 동시 업데이트 잠금, 안전하지 않은
아카이브 경로 거부, 모호하지 않은 파일별 해시 구성을 추가했다.
[업데이트·검증·롤백 절차](../backend-forge/README.md#updating-the-language)를 참고한다.

두 컨테이너는 빌드 전에 번들을 검증하고, 생성된 SDK의 헤더·라이브러리를
사용한다. 운영자가 이미지 안의 `/app/forge-toolchain.json`(서버),
`/etc/forge-toolchain.json`(Forge 프런트엔드)을 읽어 실제 포함 버전을 확인할
수 있다. 프런트엔드의 버튼 콜백 전달은 새 컴파일러의 엄격한 검사에 맞게
수정했다. 공개 API에 버전 필드를 추가하지 않았다.

## 애플리케이션 벤치마크

이전 도구체인은 portfolio 커밋 `350fda0`의 소스 스냅샷이다. 전후의 서버
`.fg`와 네이티브 어댑터가 바이트 단위로 동일함을 확인했고, PostgreSQL/web
모듈·C 최적화 `-O2`·데이터도 맞췄다. 독립된 폐기용 DB에 동일한 100개 글을
넣고 프로젝트 데이터도 복제했다. 앱별 물리 코어 2개·메모리 512 MiB·DB 풀
5개, DB는 다른 물리 코어 2개, 측정기는 별도 코어를 사용했다. 운영 서비스도
실행 중인 공유 Linux 호스트라는 한계는 있다.

각 API·동시성 조건에서 전후 순서를 균형 있게 바꾼 6쌍을 측정했다. 매번
1초 예열 후 3초를 측정했고, 예열과 본 측정 288개 시험의 **1,899,921개
요청에서 오류와 JSON 응답 불일치는 0건**이었다. 요청별 원시 지연·상태·오류,
이미지 ID, 고정된 소스와 해시를 보관했다.

다음은 구성한 클라이언트 동시성 64에서의 중앙값이다.

| API | 이전 req/s | 업데이트 req/s | 업데이트 p99 | 앱 CPU | 샘플링된 cgroup 메모리 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `/api/health` | 6,342.3 | 6,258.6 | 16.51 ms | 57.7% | 13.2 MiB |
| `/api/posts` | 2,849.0 | 2,941.7 | 34.22 ms | 67.8% | 13.6 MiB |
| `/api/projects` | 3,696.1 | 3,682.7 | 28.20 ms | 56.7% | 14.0 MiB |

CPU 100%는 코어 하나이고, 메모리는 네이티브 라이브러리·페이지 캐시 등을
포함한 cgroup 사용량이다. 할당된 힙이나 최대 RSS만을 뜻하지 않는다.

이번에 시험한 가장 높은 구성 동시성은 256이다. 업데이트 버전의 결과는 다음과 같다.

| API | req/s 중앙값 | p99 중앙값 | 반복 중 가장 높은 p99 | 오류 |
| --- | ---: | ---: | ---: | ---: |
| `/api/health` | 5,011.1 | 94.12 ms | 109.15 ms | 0 |
| `/api/posts` | 2,599.8 | 144.52 ms | 166.57 ms | 0 |
| `/api/projects` | 3,452.3 | 106.87 ms | 151.61 ms | 0 |

세 API 모두 구성 동시성 256에서 6회 전부 p99 1초 이하·오류 0건을 통과했다.
이는 폐쇄형 부하 생성기의 시험 조건이다. 실제 동시 TCP 연결·사용자 수를
세는 계측이 아니며, 절대 최대 수용 인원을 증명하지 않는다. 서버의 설정상
연결 제한도 256이다. 측정기는 모든 응답 JSON을 파싱·비교하므로 클라이언트
CPU도 처리량을 제한할 수 있다.

**12개 조건의 전후 처리량 비율 신뢰구간에 모두 1이 포함된다. 이 앱에서
유의미한 처리량 향상은 확인하지 못했다.** 동등성 검정을 한 것도 아니므로
성능이 동일하다고 보장하지 않는다. 비율은 쌍별 비율의 중앙값이며, 표의
처리량 중앙값끼리 나눈 값과 다를 수 있다. 각 구간은 6쌍으로 구한 개별
부트스트랩 구간이다. 언어 전체·모든 조건에 대한 보장이 아니다.

이 서버는 libmicrohttpd·libpq를 사용한다. 별도의 언어 연산/네이티브 epoll
벤치마크를 이 앱 결과로 대체하지 않았다. 이번 실험에는 Rust 비교군을
넣지 않았으며 Rust 110% 달성을 주장하지 않는다. HTTP 앱 측정은 Linux에서
수행했다. [모든 조건·신뢰구간·원시 기록](forge-toolchain-performance-2026-10-15.md)에
전체 결과를 보관했다.

## 검증과 적용 범위

- 업데이트 도구 7개 테스트: 커밋 내보내기·무결성·의존성 누락 시 보존·심볼릭
  링크와 Windows 경로 거부·동시 쓰기 차단·트리 해시 구분.
- 부하 생성기 3개 테스트: 정상 JSON 동등성·잘못된 HTTP 200 응답의 오류 기록·p99.
- 전체 서버 통합 테스트: DB 마이그레이션 재실행, 독립 PostgreSQL/web 모듈,
  두 nginx 프록시 보안 12개 검증, 헬스 체크의 DB 장애·시간 초과·종료 수명 주기.
- 브라우저 4개 테스트: 공개 페이지, 관리자 글 CRUD, 차단 관리, XSS 방어.
- 최종 이미지의 도구체인 명세가 최종 lock과 같고, 서버 실행 파일과 브라우저
  JavaScript가 실제 측정·테스트한 버전과 해시까지 같음을 확인했다.

측정 이후 도구체인 파일 해시 형식을 강화하고 이미지 명세 파일을 추가했다.
compiler/runtime/stdlib의 소스 파일은 측정 시점과 동일하다. 디스크 부족으로
후속 서버 빌드 로그 일부가 잘렸지만 빌드 프로세스 성공, 이미지 ID, 명세,
실행 파일/JavaScript 동일성 검증을 별도로 보관했다. 공간 확보는 제가 만든
아카이브 보관 완료 `/tmp` 중복본과 이번 빌드의 사용하지 않는 빌더 이미지에
한정했다. 운영 데이터·컨테이너·볼륨과 기존 미커밋 파일 4개는 보존했다.

운영 체크아웃과 `main` 자동 배포를 보호하기 위해 별도 워크트리와
`update-forge-toolchain-20261015` 브랜치에서 작업했다. 현재 기본 운영 구성은
Rust/React이며 이번 검증은 Forge용 서버·프런트엔드 컨테이너를 대상으로 했다.
실서비스의 Forge 전환은 저장소의 staging/rollout 검토 절차에 따른다.
